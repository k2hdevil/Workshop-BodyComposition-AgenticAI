## 만드는 앱

사용자가 자신의 체성분 분석 결과지 PDF를 올리면, 여러 에이전트가 협업해서 분석하고
회차 간 변화를 추적하며 운동·식단 계획을 제안합니다.

```
                        사용자 (브라우저)
                             │
                    Cognito 로그인 (OIDC)
                             │
                    ┌────────▼─────────┐
                    │  Streamlit 앱     │  ECS Express Mode (HTTPS)
                    │  업로드 / 추이 차트 │
                    │  보고서 / 다운로드  │
                    └────────┬─────────┘
                             │  액세스 토큰
                    ┌────────▼──────────────────────────────┐
                    │  AgentCore Runtime                    │
                    │                                       │
                    │      Supervisor Agent                 │
                    │      라우팅 · 일관성 검증 · 최종 제안     │
                    │        │                              │
                    │   ┌────┼────────────┬──────────────┐   │
                    │   ▼    ▼            ▼              │   │
                    │  체성분   운동         식단           │   │
                    │  분석    처방         제안           │   │
                    │  에이전트  에이전트      에이전트        │   │
                    │        (분석 → 운동 → 식단 순차 체이닝) │   │
                    └────────┬──────────────────────────────┘
                             │
                    ┌────────▼─────────┐        ┌──────────────────┐
                    │ AgentCore Gateway │        │ AgentCore Memory │
                    │  결과지 추출 (λ)   │        │  회차별 측정 이력   │
                    │  보고서 생성 (λ)   │        │  사용자별 격리     │
                    └──────────────────┘        └──────────────────┘
```

에이전트는 **4개**입니다. 결과지 추출은 에이전트가 아니라 **도구**입니다 — 이유는 아래 설계 결정을 보세요.

## 학습 목표

본 워크샵을 마치면 다음을 할 수 있습니다.

1. Strands Agents SDK로 멀티 에이전트를 구성하고 Agent-as-Tool 패턴으로 조율
2. 결정적 작업(문서 파싱)과 판단이 필요한 작업(해석·제안)을 구분해 설계
3. AgentCore Runtime에 CodeZip 방식으로 배포하고 Observability로 추적
4. AgentCore Memory로 시계열 측정 이력을 관리하고 회차 간 변화를 분석
5. AgentCore Gateway를 통해 Lambda 도구를 MCP로 연결하고 사용자별 데이터 격리
6. Bedrock Guardrails로 확정 진단·약물 처방을 차단하고, 개인정보 경계를 코드로 분리
7. 프롬프트·도구 캐시로 비용과 지연을 줄이고, 캐시와 컨텍스트 압축의 충돌을 이해
8. AgentCore Evaluations로 문서 추출 정확도를 Ground Truth 기반으로 회귀 검증
9. Streamlit 앱을 ECS Express Mode에 배포하고 Cognito 인증을 연결

## 샘플 데이터

같은 사람의 **3회차 측정 + 다른 사람 1회차**, 총 4건입니다. 추이 분석은 서로 다른 두 사람으로는
검증할 수 없기 때문입니다.

| 문서 | 인물 | 측정일 | 형식 | 역할 |
|------|------|--------|------|------|
| `user-a-session-01` | 김도현 44세 남 | 2026-02-14 | **스캔본** | 추이 기준선 · 비만 |
| `user-a-session-02` | 김도현 | 2026-05-16 | 디지털 | 개선 진행 |
| `user-a-session-03` | 김도현 | 2026-08-14 | 디지털 | 최근 · 델타 분석 |
| `user-b-session-01` | 박지은 32세 여 | 2026-08-18 | 디지털 | 다른 사용자 · 저체중 |

의도적으로 심어둔 함정이 있습니다.

- **1회차는 텍스트 레이어가 없는 스캔본입니다.** 구조 파서만 쓰면 실패하고, 비전 폴백이 있어야 통과합니다.
- **user-b는 D자형인데 세 지표가 모두 표준 미만입니다.** "D자형 = 이상적"으로 답하면 오판입니다.
  실제 소견은 저체중 + 근육량 부족이고, 권고 방향이 user-a와 정반대여야 합니다.

자세한 내용은 [sample-data/README.md](./sample-data/README.md)를 보세요.

## 결과지 구성 (4개 섹션)

| 섹션 | 영문 | 내용 |
|------|------|------|
| 체성분 분석 | Body Composition Analysis | 체수분 / 단백질 / 무기질 / 체지방량 |
| 골격근·지방 분석 | Muscle-Fat Analysis | 체중 / 골격근량 / 체지방량 → C·I·D 체형 판정 |
| 비만 분석 | Obesity Analysis | BMI (겉보기 비만도) / PBF (실제 체지방률) |
| 부위별 근육 분석 | Segmental Lean Analysis | 오른팔 / 왼팔 / 몸통 / 오른다리 / 왼다리 |

체형 판정은 세 막대의 끝점을 연결한 형태로 읽습니다.

- **C자형** 체중·지방에 비해 근육 부족
- **I자형** 세 지표가 표준 범위에서 균형
- **D자형** 체중에 비해 근육 많고 지방 적음

체지방률 표준은 **남성 10~20%**, **여성 18~28%** 입니다.

## 핵심 설계 결정

이 워크샵이 특정 선택을 한 이유입니다. 교육 포인트이기도 합니다.

### 결과지 추출은 에이전트가 아니라 도구입니다

PDF를 열고 값을 뽑고 검증하는 일은 결정적입니다. LLM 루프를 씌우면 지연·비용·비결정성만 늘고
얻는 게 없습니다. 다만 결과지 레이아웃이 기기·연식별로 다르므로, 구조 파싱이 실패하면
비전 모델로 폴백합니다. 그것도 **모델을 한 번 호출하는 도구**이고 자율 루프를 가진 에이전트가 아닙니다.

```
@tool extract_body_composition(s3_key)
 ├─ 1차  pdfplumber 구조 파싱      텍스트 레이어 PDF · LLM 호출 없음 · 결정적
 ├─ 2차  Converse document 폴백    스캔본 · Bedrock이 페이지를 시각 분석
 └─ 검증  체성분 합 = 체중, BMI 재계산 (코드)
```

**둘 다 순수 Python이라 네이티브 의존성이 없습니다.** 실측으로 확인한 사실인데, Bedrock
Converse의 document 블록은 텍스트 레이어가 없는 스캔본도 **별도 설정 없이 자동으로** 읽습니다.
그래서 래스터화 라이브러리(PyMuPDF·poppler)나 Code Interpreter가 필요하지 않습니다.

1차에 `pdfplumber`를 두는 이유는 텍스트 PDF에서 LLM 호출 없이 결정적으로 뽑는 편이 비용·지연·
재현성 모두 낫기 때문입니다. Lab 1에서 두 경로의 토큰 사용량을 직접 비교합니다
(같은 결과지가 텍스트 경로 3,181 토큰 / 이미지 경로 1,654 토큰).

### 결과지에서 추출한 이름으로 보안 판단을 하지 않습니다

본인 확인을 위해 로그인 사용자 이름과 결과지 이름을 대조하는데, **스캔본에서 한글 이름이
체계적으로 오독됩니다.** 실측에서 `김도현`이 `김도원`으로 5/5회 재현되어 오독됐습니다
(수치는 전부 정확했습니다). 재시도로 해결되지 않습니다.

그래서 완전일치로 차단하면 정당한 사용자가 막힙니다.

| 판정 | 처리 |
|------|------|
| 완전일치 | 통과 |
| 편집거리 1 이하 | **경고 후 진행** — 사용자에게 본인 여부를 확인 |
| 그 외 | 차단 |

교육 포인트는 **OCR 결과로 보안 판단을 하면 안 된다**는 것입니다. 이름을 에이전트 컨텍스트에서
제외한 결정도 같은 근거를 공유합니다 — 이름은 가장 신뢰할 수 없는 필드입니다.

### 운동과 식단은 순차로 체이닝합니다

두 에이전트를 독립 실행하면 모순된 계획이 나옵니다. 식단이 큰 칼로리 적자를 제안하는데 운동이
고강도 근력을 처방하면 근손실을 유발합니다. 그래서 **분석 → 운동 → 식단(운동 계획을 입력으로 받음)**
순서를 고정하고, Supervisor가 일관성을 검증합니다.

### 개인정보는 마스킹이 아니라 경계로 다룹니다

본인이 본인 결과지를 보는 앱이므로 화면에는 이름이 나와야 합니다. 대신 경계를 나눕니다.

| 경계 | 이름 | 나이 | 처리 |
|------|------|------|------|
| 화면 (사용자) | 표시 | 표시 | Cognito 프로필의 이름 사용 |
| 에이전트 (LLM 컨텍스트) | **제외** | 필요 | 이름은 분석에 아무 역할도 안 함 |
| 로그 · 트레이스 · Memory | **제외** | 제외 | Cognito `sub`로 대체 |

애초에 LLM에 보내지 않으면 마스킹할 필요가 없습니다. Guardrails는 최후 방어선이지 1차 방어선이 아닙니다.

결과지에서 추출한 이름은 **표시용이 아니라 본인 확인용**입니다. 로그인 사용자와 결과지의 이름이
다르면 타인의 결과지 업로드로 판단해 경고합니다.

### Guardrails는 실제로 존재하는 위험을 막습니다

| 위험 | 이 앱에서 벌어지는 일 | 대응 |
|------|---------------------|------|
| 확정 진단 | 체지방률 32.5% + 내장지방 15 → "대사증후군입니다" | 거부 주제 (DENY) |
| 약물·보충제 처방 | 특정 약물명이나 용량 제시 | 거부 주제 (DENY) |
| 간접 프롬프트 인젝션 | **업로드된 PDF 안에 악성 텍스트 삽입** | `PROMPT_ATTACK` 필터 |

세 번째가 이 앱 고유의 공격면입니다. 사용자가 올린 파일 내용이 그대로 LLM 컨텍스트에 들어갑니다.

### 캐시와 컨텍스트 압축은 경계를 나눠야 합니다

캐시는 안정된 prefix를 요구하고, 압축은 대화 이력을 재작성해 그 prefix를 깨뜨립니다.
순진하게 같이 쓰면 캐시 적중률이 0이 됩니다.

```
[ 시스템 프롬프트 + 도구 정의 ]   <- 캐시 (변하지 않음)
[ 정규화된 측정 데이터 ]          <- 캐시 (세션 내 고정)
[ 대화 이력 ]                    <- 압축 대상 (캐시 경계 뒤)
```

Claude Sonnet 4.5의 캐시 최소 토큰은 **1,024**이고 체크포인트는 최대 4개입니다.

### Runtime 배포는 CodeZip, 프론트엔드 배포는 ECS Express Mode입니다

에이전트 Runtime 은 Docker 빌드·ECR push 가 4시간 세션의 실패 지점이라 **CodeZip(Direct
Code Deploy)** 으로 배포합니다. zip 업로드만으로 배포되고 콜드스타트도 더 짧습니다.

프론트엔드(Streamlit)는 원래 App Runner 로 배포할 계획이었으나, **App Runner 가 신규 고객
접수를 종료**해 워크샵 임시 계정에서는 쓸 수 없습니다. 대체로 **ECS Express Mode** 를
씁니다 — 컨테이너 이미지 하나로 Fargate 서비스·HTTPS 로드밸런서·오토스케일·URL 을 자동
구성합니다. 컨테이너가 필요하지만 **프론트엔드 한 개만 얇게 컨테이너화**하므로(Dockerfile
6줄, ECR push 1회) Runtime 의 CodeZip 결정과 충돌하지 않습니다.
